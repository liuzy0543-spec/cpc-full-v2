## 3. 逐条详述与修订文本

### P0-1（**已撤回**）ca_mae 的 value_range 没有被强制执行

> **结论：本条为误判，2026-10-26 第二次复核时撤回。** 保留原文与证据，供后续审查者避免重复同样的错误。

**当初的判断**：ca_mae 声明 `value_range=(0,255)`，却接受 max=65535 的 uint16，故 §6.2 W4 不成立。

**错在哪（三点）**：

1. **测错了路径**。ca_mae 在 `registry.py:289` 声明了 `source_map='per_crop_max255'`；`assume='raw_crop'` 的语义正是"这是原始采集值，请按声明的 source_map 换算"。带 assume 时接受 16-bit 原始值是**设计意图**，不是守卫失效。
2. **机制解释也错了**。当时说"嵌入逐位相同是因为 `257n mod 256 = n` 的算术巧合"。实测同一批像素乘 ×1 / ×2 / ×16 / ×257 走 assume 路径，四条结果 `max|diff|` **全部为 0**——真正的机制是 `per_crop_max255` 对正的标量倍数不变（尺度不变性），与 257 和 256 无关。
3. **正确的测法**（不带 assume、布局正确的 BCHW）守卫确实会拒：

```
IncompatibleInput: Input is not compatible with model 'ca_mae':
[value-range] input values span [0, 65535] but 'ca_mae' declares (0.0, 255.0); scale='div255'
```

**附带教训（值得写进审查方法论）**：第一次的测试脚本用 `if 'assume' in name` 分支，而用例名写着"不带assume"——**字符串里含有 `assume` 子串**，导致四个用例全部走了 assume 路径。这种"看起来在测 A、实际在测 B"的错误不会报错，只会给出一份看起来正常的结论，正是本提示词铁律 5 警告的情形。**测试分支不要靠字符串匹配用例名。**

**修订版的处理是正确的**：§6.2 W4 已改为"对每个声明了 value_range 的方法，喂越界数组**且不带** assume"，§8.10 也单列了 source_map 并区分两条路径。**这一条不需要再改。**

### P0-2（阻断）答案纸问题：通过退化为数字比对

**位置**：§4.2 基线表、§5.1 一行式自检、§7 判据 1

**问题**：提示词给出了 mAP_z 四位小数、4 个官方权重与 3 个替身权重的 sha256 前 16 位、107 passed / 317 passed / 9 skipped / 14 failed、七方法输出宽度。§7 的核心判据就是"必须与这些数字逐位一致"。

**修订**：在 §5 之前插入「随机探针」小节，要求审查者回报至少三个**本文档未给出**的量，例如：

```markdown
### 5.0 随机探针（必须回报，本文档不给答案）

审查者必须在报告开头回报下列值；缺任一项，整份报告按"未执行"处理：

1. embed('deepprofiler', dp[:2], assume='raw_crop').as_numpy() 第 0 行前 8 个 float32 的 sha256 前 16 位
2. models.describe() 的 v3 列表中，按名字排序后的**第 4 个**方法名

4. 你所测得 v2 四个方法 mAP_z 的**最小值与最大值之差**（三位有效数字）
```

这些值不可猜、必须实跑才能得到；同时不破坏原有"偏差即回归"的判据。

## 4. 建议新增的两条审查项

### §8.10 攻击 value_range 守卫本身

```markdown
对**每一个**在 manifest 里声明了 value_range 的方法，各喂一次越界输入：

| 方法 | 声明值域 | 越界输入 | 期望 |
|---|---|---|---|
| ca_mae | (0, 255) | uint16 max=65535 | 拒 value-range |
| ca_mae | (0, 255) | float32 max=65535 | 拒 value-range |
| ca_mae | (0, 255) | **非 ×257 的 uint16**（如 0..4095 的 12-bit 数据升 16 位） | 拒，或给出**逐位**证据说明为何无害 |
| unidino | (0, 65535) | uint8 | 拒 value-range |
| morphogenie | (0, 1) | uint8 | 拒 |

**已知结论**：ca_mae 接受 uint16 max=65535，未拒。请复核并给出你的实测。
另需判明：257n mod 256 = n 这个恒等是否被代码**有意**利用；
若是巧合，则任何非 ×257 的 16-bit 数据都会静默截断。
```

### §8.11 攻击 benchmark 的有效性

```markdown
§7 要求逐位复现排序，但**没有要求判断排序有没有意义**。请补做：

1. 随机基线与每个方法的差：o2vae 0.0471 − 随机 0.0450 = 0.0021。这个差相对跨 fold 波动是多少？
   把 stability_check.py 的 4 fold 结果拿出来，给出每个方法的 fold 区间。
2. silhouette 全为负意味着嵌入不可分簇。那么"方法 A 优于方法 B"这一判断，
   在**没有可分离结构**的数据上依赖的是什么？
3. 若某个方法的 fold 区间与随机基线重叠，必须在 §9 结论里写明"该方法的排序不成立"。
4. 明确回答：在 mock-AUC 随机基线 0.4996、silhouette 全负的前提下，
   "v2 可发表"是否仍然成立？若不成立，需要补什么实验才能成立？
```

### 8-1 🔴 F 系列表格被插入内容打断，F13/F14 失去表头

```
169| | **F12** | ... |
170|                                     ← 空行：表格在此结束
171| > **F8 / F9 / F12 标「有意保留」不等于免检** ...
```

GFM 表格在空行处终止；179–180 两行**没有表头也没有分隔行**，会被渲染成普通段落文字，而不是表格行。下游若有工具按表格解析，F13/F14 会直接丢失。

**修法**：把引用块移到 F 系列表格**结束之后**（第 181 行空行处），或将 F13/F14 行上移回表内、把引用块整体下移。

### 8-4 🟡 B14 承诺的校验与 §8.5 的测法不是同一件事

- **B14（第 309 行）**：「三个替身的 `weights_sha256` 与 manifest 钉住的值一致，**且被替换的文件必须被拒**（§8.5）」

**改名 → 文件不存在**，走的是"权重缺失"分支；**"被替换"（文件存在但内容不符）**走的是另一条 sha256 校验分支。§8.5 的改名测不到 B14 承诺的那件事。
